# 架构原则

## 按责任划分

按业务含义和变化原因组织模块。共同变化的内容放在一起，每条规则和每份状态有明确的所有者。

保留顶层分层，在层内按领域聚合。工具契约与执行适配放在一起；服务负责业务决定和状态转换；存储负责可靠保存；接入层处理宿主协议；UI 展示数据并返回用户选择。共享目录只放多个领域实际共用的逻辑。

## 复用宿主

Pi 负责主会话、模型配置、工具、UI、资源发现与会话恢复。Personal Bot 补充资料准备、专家协作和 Python 环境。

角色定义职责，技能描述专业方法，代码实现需要确定执行的规则。优先使用原生 CLI/MCP，执行权限由实际凭据、外部服务和运行环境约束。

## 保持单向依赖

服务接收普通数据与窄能力，宿主细节留在接入层。命令与工具调用同一服务。依赖边界与循环由 dependency-cruiser 检查，具体分层见[技术设计](technical-design.md)。

资源的创建、状态变更和释放由同一责任主体管理。工具绑定工作区实例，实例关闭后旧调用失效。

## 控制复杂度

围绕已确认的需求实现最简单的方案。只有出现实际协议差异或复用需求时才引入策略和抽象。删除无用代码，避免转发层、重复状态和通用平台化。

局部需求反复牵动无关模块时，先调整责任划分。已有资料与历史记录保留原样；恢复操作遵循[工具与执行](capability-design.md)中的副作用规则。

## 验证行为

测试业务契约和具体失败风险，使用真实本地文件、进程、计算和 Pi SDK。测试不依赖假模型、模拟 provider、个人凭据或真实交易，也不以文案和实现结构作为行为断言。

本地测试与外部验收分别记录，范围见[验证](validation.md)。

## 维护文档

文档组织见[索引](README.md)。使用方法、行为或接口变化时更新所属主题；内部重构只更新受影响的设计说明。

描述当前规则及必要理由，使用短句和一致术语。运行时提示词与开发文档分开维护，避免把开发细节加入模型上下文。
