# 模型指令编写原则

修改 Agent 实际可见的内容及其加载方式时遵循本文。范围包括 Pi 与 dsh 的主会话、专家、历史摘要，以及公共提示、角色、动态环境、团队消息、通知、工具说明、技能、参考资料和模板。当前加载方式见[模型上下文](model-context.md)。

## 从实际上下文出发

以宿主实际组装的内容判断取舍，尤其检查新会话第一次任务。同时考虑宿主提示、用户资料、工具声明和技能目录，避免只看某个 Markdown 文件。

每段指令应有具体用途：它帮助模型作什么决定、执行什么操作，或者避免什么已知错误。根据用途保留、合并、删除、条件加载或按需读取，不以字数最少为目标。没有明确需求的规则不要因为“看起来更严谨”而加入。

## 直接说明要做什么

使用自然、直接的语言，写清职责、操作入口、参数含义和下一步。内部架构与执行机制只在改变实际操作时说明，其余留在开发文档。

例如，委派时说明目标、相关资料、约束和交付要求即可，不需要再向模型解释“不继承父聊天历史”。状态、分页、通知领取和异步完成等含义会影响工具调用，应保留必要细节。

## 不增加泛化流程

按用户请求和已有约定推进，不自行补入通用的证据收集、授权核对、审批、独立复核或业务验收流程。不在公共提示、角色、工具和通知中反复写“不扩大授权”“不等于成功”等提醒，也不为普通交付固定证据报告或复核结论格式。

具体任务需要查来源、复核计算或检查结果时，写明实际要检查什么。专业方法可以保留影响结果的口径、假设、数据处理和适用条件；常规操作不因此变成逐项审批或留证任务。独立复核按用户需求或具体问题安排，不设为默认必经步骤。

权限和确认机制沿用宿主、凭据、外部服务及用户约定。不要为假设风险新增提示门槛，也不要通过提示掩盖或绕过实际执行限制。保留直接影响操作的事项，如配置作用域、凭据引用、内容公开范围，以及结果未知时先查状态、避免重复执行。

## 保留实用细节，按用途放置

| 内容 | 放置要求 |
| --- | --- |
| 首次任务就需要的职责与资料位置 | 放在公共提示或对应角色中 |
| 工作区目录用途与组织规范 | 保留首轮可见的目录说明和模板导航；不能只藏在尚未选择的维护技能里，已有用户布局与约定优先 |
| 工具参数、分页、状态和结果入口 | 放在工具契约中，避免其他提示重复完整说明 |
| 团队等特定任务说明 | 仅在相应任务或状态下加入 |
| 维护、接入、计算及调度方法 | 通过技能或参考资料按需读取，正文包含能实际执行的方法和必要细节 |
| 动态环境与错误 | 提供当前操作需要的字段；详细诊断留在状态或日志入口 |
| 历史摘要 | 使用专用提示与待总结资料，不混入普通工作角色和无关技能 |

优先使用宿主已有的资源发现、技能、工具、配置和上下文去重机制。检查同一要求是否已由宿主或其他已加载内容提供；专用说明不要无条件叠加到所有会话。

## 在正确位置修复

先区分提示内容、上下文组装、功能实现和测试问题。加载缺失、时序错误、重复注入或错误处理问题应修代码；不要增加提示规则来补偿。

发现一类问题后，检查两个宿主及其他相关入口，包括代码生成的任务、通知和工具结果。复查既有处理是否过度定制，不为单个案例继续叠加规则。

修改插件自身的内容与加载逻辑，保留用户资料、角色补充、历史和备份。不要为了整理提示而迁移用户布局、覆盖用户约定或改变既有执行合同。

## 检查

加载行为用真实宿主 SDK、本地文件和进程检查来源、首轮出现时机、后续更新、条件加载及去重。测试应覆盖具体行为，不能断言提示句子、标签或全文快照；不能为了满足文案断言反向修改提示，也不为纯文案调整新增此类测试。

运行适用的仓库检查。设计文档维护当前行为；本次结果与未决问题在任务或 PR 中说明。
