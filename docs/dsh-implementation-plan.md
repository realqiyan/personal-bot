# dsh 双宿主实施技术方案

状态：双宿主实现及本机 SDK、分发、Web 和桌面验证已完成；2026-11-06 的 Linux CI 全量检查通过，成功模型工作流仍待验收。产品边界见[双宿主方案](dsh-support-proposal.md)，分批验证结果见[验证](validation.md)。

## 目标与完成条件

在同一个 `personal-bot` npm 包中保留 Pi 入口，增加 dsh 服务端和 Web 客户端入口。两端共用资料、业务规则和历史查询；各自管理原生会话、模型、认证、配置与执行生命周期。dsh 首轮实现与当前开发依赖基线为 `0.2.2-rc.1`，开发和完整验证使用 Linux、Node.js 24.9.0 以上。用户安装跟随 `latest`，包声明只设最低宿主版本；保留精确开发依赖与锁文件以复现检查。本文后续“固定版”指这批实施记录的版本，不限制用户更新。

交付必须覆盖专家、团队、通知、history、共享 Python、资源、文件确认及人工管理。接入验证和部分功能可作为实施里程碑，不能被表述为完整支持。先验证真实接口，再调整共享服务，避免以假定 API 建立大范围改动。

## 专家与异步边界

现有 `AgentHost` 的同步创建、恢复校验和报告读取需要支持 dsh 原生异步接口。保留同步的本地状态查询；异步操作在共享服务中显式等待，调用方逐层传播，不把 Promise 放入同步文件锁。

创建与恢复分为以下步骤：

1. 核对实例、工作区、父会话、兼容线与模型选项。
2. 在短控制锁内完成同一父会话的 50 个存活/启动中专家限额准入，保存新 generation 和启动状态。
3. 锁外创建或恢复原生 Agent，在 setup 中安装资源及监听器。恢复时校验原生身份、cwd 和父级，清除旧 native inbox。
4. 使用 `SessionStore.flush` 等公开持久化屏障确认空会话已落盘。屏障缺失或失败时不能宣布 start 成功。
5. 再核对 generation、stop 和实例；过期则释放原生句柄。通过后才接纳本 generation 的新要求。

Pi 继续保留原始 `session-ref.json`、路径与 leaf。dsh 使用独立的原生 Session 引用及持久位置，不给 Pi 文件字段填入 Session ID。业务层只传递引用，不解析 SDK 事件。

从 `extension/subagent-entry.ts` 提取两端实际需要的领取、周期、人工输入归因和中断规则。原生事件转换为请求消费、周期开始、结束原因及固定位置等普通数据。成功判定要求已消费请求、有效轮次结束和非空最终答复；idle 不是成功凭据。

stop 先保存停止意图，再取消和释放句柄；释放未完成时保留占用与 stopping 状态。恢复只执行新要求，不自动重放旧 generation 或旧团队批次。只读查看不恢复执行。

## 生命周期、团队与通知

服务端组件持有进程级 Python 激活；工作区持有共用历史整理器；父 Session 持有专家、团队和调度器；专家持有 AgentHandle。页面只观察这些资源。使用服务端实例信号承接已接受的工作，不能让浏览器断连信号取消已接受任务。

团队继续使用现有算法。主会话 send 遵循 `TEAM_BUSY`；专家直接人工输入归为 interactive，混合周期为 mixed，暂停团队且不自动公开混合答复。公共原文注入下一安全边界，普通 post 不开启模型轮次。

通知按 agent/cycle 或 team/run/状态去重。模型领取报告与 UI 浏览分开。异步回调核对实例和 generation；父 Session 关闭或执行组件卸载后，旧工具与 Remote 调用失效。

## History

Pi 只维护 `.pi/pbot/history/`，dsh 只维护 `.dsh/pbot/history/`，两端查询双方归档。来源由归档目录确定，关联键为 host 与 sessionId，不重写旧 Pi 节点。新 dsh 根 ID 使用 `dsh-<uuid>`。

`search` 增加可选 host 筛选；结果、导航和 read source 带来源。原有正文、关系分页和 Pi ID 语义保留。dsh 接入仅通过公开 Session query/persistence 读原生日志，不扫描另一宿主的原生记录，也不触发 Pi 旧归档导入。

摘要只在本宿主正常交互结束后安排。查询和重连不得调用模型。模型调用在短写锁外；提交前重读归档并核对原文和子节点，丢弃过期结果。dsh 使用原生 LLM 接口，复用当前模型和认证，不写入主聊天。完整工具日志由专家视图读取，不能用问答归档替代。

## Web 与安装

原生命令提供 `/pbot init`、`status`、`python setup` 及专家、团队、history 入口。Web 模块通过 dsh 原生 Remote 查询和操作同一服务，提供专家完整记录、直接对话、停止/恢复，团队操作与 history 展开。查询路径不得隐式激活 Agent。

bundle patch 基于原生 Web profile，声明默认 pbot 组合、服务端插件和客户端依赖。固定版客户端发现只接受包根 Loader 名称，因此 `personal-bot` 包根导出作为 dsh 服务端入口的别名，bundle 使用包根名称加载；`personal-bot/dsh` 独立入口仍保留，Pi 继续显式加载源码入口。客户端遵守固定版本 module loader 格式；外部复用 Cordis、React 和原生 UI。宿主包为可选 peer，开发依赖固定版本，不在发布产物打包第二份 SDK。TypeBox 是共享契约库，声明为范围为 `"*"` 的必需 peer，并在开发依赖中锁定版本。Pi 原生加载器提供 TypeBox；dsh 不提供它，由包管理器在安装时补齐，不能依靠 Pi 的安装间接供应。固定版 dsh 的输出 schema 只支持结构约束和 `oneOf`，因此协作工具保留完整生产端校验，并向宿主提供去除 TypeBox 元数据、采用互斥分支的结构 schema。

安装使用原生插件流程。`--from-default-profile` 仅用于首次创建，不作为升级命令。Pi 安装 CLI 不扩展为 dsh 配置管理器。`prepack` 生成 CLI、dsh 服务端和 Web 产物；`dist` 仍只用于测试。

## 接入验证记录

- 固定发布包的真实 Cordis、AgentLoop、JSONL persistence 和内存 query：空专家经 flush 后可被独立进程读取；冷恢复保留身份；恢复 setup 清除旧 inbox 后没有开启旧轮次；错误归属或缺失记录不会激活或替换会话。
- 使用原生 Session API 写入轮次记录，验证报告固定到持久的 `turn/end`，后续对话及 Agent 释放不改变旧报告。
- 原生 Bash 在 spawn 时读取进程 venv，两个工作区保留各自 cwd，禁用 user site，环境恢复通过。原生命令的两个父会话分别绑定工作区；关闭一个不影响另一个；卸载插件后旧 handler 失效。
- Linux Node.js 24.15.0 的初始完整检查通过：`npm ci --ignore-scripts`、`npm run check`、`npm test`，103 项测试通过。之后新增的固定报告及工作区生命周期测试已在本地通过；该接入检查点尚未重跑最终 Linux 全量检查。
- npm tarball 经原生插件命令安装到隔离 `pbot` profile；真实 Chrome 打开 Web，选择临时工作区，展开 `/pbot` 菜单、执行 status 和 init、刷新后再次查询，工作区和父会话身份保持一致，没有 pageerror。客户端需要同时声明 `remote` 与 `remote.commands` 注入。包根发现规则及 Remote 依赖问题已修正。
- Web 测试中的 Python 目录刻意包含无关数据，原生 setup 如实返回错误且没有覆盖该数据。该测试不证明完整 Python 依赖安装成功；真实计算环境测试由既有 Python 验证及原生 Bash 测试覆盖。

这些结果只证明接入与无模型生命周期边界。专家完整工作流、执行中页面断开/组件关闭、团队、history、文件确认与模型结果仍在后续阶段验收。

公共边界回归已完成两轮 Linux 全量检查，108 项测试全部通过。`AgentHost` 的创建、校验、报告读取和释放支持异步；启动预约计入限额，恢复校验期间停止不会更换 generation 或写入新输入，关闭等待实际释放。`AgentRun` 统一保存领取、消费、周期与人工输入归因，并封存结果未知的旧领取；Pi 原有文件引用和完成记录格式保留。专家/团队动作处理及公共原文格式化已拆离 Pi 适配。异步扫描发现的会话树事件等待问题已修正，通知恢复与故障升级的原有测试通过。

阶段 C 已接入每个父会话的专家与团队服务、原生工具、角色与技能提供方、附件保存和服务端调度。请求先保存领取，再按原生 inbox 进入轮次、`user/message` 消费及持久 `turn/end` 分别记录；原生领取本身不满足成功条件。人工输入在领取时归入对应周期，在消费后才能支持成功判定；等待未来轮次的人工输入不会把此前的答复误标为 mixed。

当前实现状态见下列阶段 D 记录。阶段 C 检查点的 `npm run check`、构建、差异检查与 19 项定向测试曾全部通过。新增真实原生工具测试验证原工作区固定、归属拒绝、空专家不启轮次、显式恢复与原模型选项保留、缺失 provider 的真实失败、团队有限批次失败暂停且不发布失败答复。真实 Agent maintenance 中运行原生 Bash，验证关闭一个父会话等待其进程退出且另一父会话继续，组件卸载等待剩余进程退出。未安装模型适配器，没有伪造模型回答。创建专家也先 flush 父会话，冷恢复测试因此使用原生 resume 恢复既有父身份。

完成通知复用共同的团队/个人选择和格式规则。dsh 以已提交的 `user/message` 或成功模型工具结果确认领取；PTC 内层 read 还须外层调用成功。原生 inbox 中的排队通知只防止重复提交，不冒充消费。没有正常交互的冷加载和只读查看不会唤醒模型；实际接纳通知或新的人工输入才重新允许自动跟进，失败准入不形成自动重试循环。主会话中断先暂停团队，后台仍核对在途工作；暂停与报告读取故障分别报告。Pi 的三项通知故障与恢复测试通过；测试临时工作目录规范化，避免 macOS 的 `/var` 符号链接造成无效工作区 fixture。

原生 `write`、`edit`、`apply_patch` 已接入文件规则。整份 patch 的源与移动目标先检查，执行前重核 cwd 和目标身份；专家工作区外直接拒绝，主会话使用原生一次批准。真实文件测试覆盖内部修改、符号链接外逃、move 和混合补丁拒绝，以及原生 `rejected`/`unavailable` 审计。真实附件服务验证二进制文件跨块保存后原字节可读、图片准入、原路径删除后附件仍可读，以及目录、取消和图片数量上限拒绝。图片总字节与数量在批量载入期间按宿主限额检查。

阶段 C 检查点当时未完成 Linux 回归：服务器 SSH 不可达，本机没有 Docker、Colima、Lima 或 Podman，先前 C1 安装未取得成功退出证据。这是历史检查点记录；当时浏览器产物只到阶段 A，后续审批、资源与管理验收结果见下文。

阶段 D 的 history 服务和原生工具已接入。两个来源可共同搜索、分别维护；Pi 旧 ID、摘要、关系、分页和旧归档导入继续保留，dsh 不清理或导入 Pi 归档。公开 Session query 读取当前工作区及关联专家，按父级归属纳入不同 cwd 的专家，不把别的工作区专家因 cwd 相同而混入。普通 fork 保留为自身的原生会话；`isSeeded` 是 fork 标记，不是应排除的模板标记。人工 steering、未结束或截断答复保留为原文，工具记录仍由完整原生视图提供。

每个工作区共享一个服务端整理器，正常主交互结束后安排，其他父会话尚在交互或有待输入时不启动；新人工输入和下一原生 step 会取消整理。原生 `llm.prepareCall` 与 `stream` 复用当前模型及认证，采用宿主声明的最低 reasoning effort，单独处理纯文本且不写主聊天。摘要和扫描均在短写锁外准备，提交时重读；原文或子节点变化时放弃旧结果，已经保存的摘要优先。失败保留待整理节点并暴露警告，查询不会调用模型。

本地类型、依赖检查（121 个模块、497 条依赖）、构建、差异检查和 28 项定向组合已通过，覆盖 AgentRun、Pi 通知、全部 dsh 测试及 history。新增测试使用真实 Session、双来源归档和两个 Node 进程；FIFO 仅承载真实 SDK JSONL，用操作系统读写屏障验证慢扫描不能覆盖另一进程的新索引，没有替代来源或模型。测试还覆盖同一原生 ID 的来源区分、来源损坏隔离、旧 Pi 身份与摘要、冷读不激活、取消查询不取消后续刷新、过期摘要拒绝、实际缺失提供方的失败，以及同工作区关闭一个父会话后继续查询。随后补充未加载索引状态区分，相关 10 项 history/工作区回归及检查、构建和差异检查再次通过。

同时收紧了两项原生边界：最终答复需要持久流的 `stop` 标记，工具调用文本和 token 截断不满足成功条件；团队投递使用原生 maintenance 的空闲准入，避免把其公开的 `idle` 状态当作真正空闲。真实 Bash maintenance 验证团队要求在维护结束前没有进入 inbox。外部原生句柄占用也计入存活，恢复被拒绝且 generation 不变；当前组件不能假称已释放别的执行实例。组件卸载会撤销其挂在父会话上的 effect，释放历史缓存。

Web 管理已接入固定版公开的 `TypertRemoteService`、`Remote` 和 Typert 注册接口。四个查询描述符由 Host 与 Client 共用，Host 按组件注册，Client 通过原生 `$mount` 挂载；没有私有 HTTP 或额外类型编译框架。读取、轮询和完整原生记录使用查询方法；原生命令会追加 `command/run`/`command/done`，不能拿它反复轮询页面。原生记录按事件分页，正文与完整事件都能继续读取长内容，停止后的专家仍可冷读。人工写操作复用命令、工具的业务动作，命令不重复记录私人输入正文。

`/pbot` 的裸调用打开工作区、专家、团队和历史管理页；带参数的原生命令支持 `agent`、`chat`、`team`、`post`、`history`、`records`。页面保存自己的表单与选择，只取消查询，已经接纳的执行归服务端所有。人工对话支持服务器文件及原生输入框已准入附件，先成功暂停所属团队再进入 inbox；人工输入待进入时停止追加团队上下文。原生 registry 的根归属用于识别协调者，不只依靠可选的 origin 标签。改变 provider 或 model 时，不再把父会话的 reasoning effort 带到另一模型。

新增真实 SDK 管理测试覆盖只读查询不写主会话、不启动空专家、完整记录分页、停止后冷读、父归属、未标注 origin 的原生子 Agent、组件卸载后的失效、暂停锁失败时不接纳人工消息，以及实际缺失 provider 的失败。该测试没有模拟模型。

## 优先核查的风险

| 风险 | 验证与处理 |
| --- | --- |
| 空会话延迟落盘 | 真实创建、公开 flush、释放、冷读取与恢复；不插入假消息促使落盘 |
| 恢复自动消费旧 inbox | 在 setup 中清除旧输入，验证发布前顺序；只接受新 generation |
| 服务端所有权与页面生命周期耦合 | 两个父会话、断开观察、组件卸载分别验证 |
| 同进程专家无法强杀 | 验证协作取消及 dispose；阻塞时保持真实状态和占用 |
| 客户端发布格式或依赖解析不匹配 | 使用真实 tarball 在隔离 Web profile 加载，检查 Remote 与原生 UI |
| Pi 既有存储被异步改动破坏 | 先完成 Pi 回归，再接入 dsh；原始数据不迁移 |
| 固定预发布包缺少必要公开能力 | 保存可复现证据与具体影响，报告需重审的决定，不静默改版本或缩减范围 |
